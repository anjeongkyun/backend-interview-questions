# SQL 인젝션

> 문자열을 붙이는 순간 데이터가 코드가 된다

## 이 개념을 왜 묻나

**"입력을 검증한다"로 답하는지, "쿼리와 데이터를 분리한다"로 답하는지**가 갈립니다. 앞은 막다가 새고 뒤는 원리적으로 막습니다. 이 차이를 아는지 보는 질문입니다.

## 질문

### SQL 인젝션은 왜 생기고 어떻게 막나요?

<details>
<summary>답변</summary>

**사용자 입력을 쿼리 문자열에 붙여** 데이터가 SQL 문법으로 해석되기 때문입니다.

```java
// 취약
String sql = "SELECT * FROM users WHERE email = '" + email + "'";
```

`email` 에 `' OR '1'='1` 이 들어오면 조건이 항상 참이 됩니다.

막는 방법은 하나입니다. **쿼리와 데이터를 따로 보냅니다.**

```java
String sql = "SELECT * FROM users WHERE email = ?";
ps.setString(1, email);
```

바인딩하면 DB 가 `?` 자리를 **값으로만** 취급합니다. 무엇이 들어와도 문법으로 해석되지 않으므로 이스케이프를 신경 쓸 필요가 없습니다.

**판단 기준:** 문자열 연결이 보이면 의심합니다. ORM 을 쓰더라도 직접 쿼리를 만드는 부분(네이티브 쿼리, 동적 정렬, `IN` 절 조립)에 구멍이 생깁니다.

**흔한 실수:** 특수문자를 걸러 막는다고 답하는 것. 인코딩 우회, DB 별 문법 차이, 주석 삽입으로 빠져나갈 길이 계속 생깁니다. **차단 목록은 언제나 불완전합니다.** 그리고 "우리는 ORM 이라 안전하다"도 위험합니다. ORM 은 기본 경로만 안전하게 해줍니다.

</details>

### 바인딩할 수 없는 부분은 어떻게 다루나요?

<details>
<summary>답변</summary>

**테이블명, 컬럼명, 정렬 방향은 바인딩되지 않습니다.** 값이 아니라 문법이기 때문입니다.

```sql
-- 이건 안 된다
ORDER BY ? ?
```

정렬 컬럼을 사용자가 고르는 화면에서 이 문제가 생깁니다. 방법은 **허용 목록**입니다.

| 방식 | 안전한가 |
|------|----------|
| 입력값을 그대로 `ORDER BY` 에 붙인다 | 취약 |
| 특수문자를 걸러 붙인다 | 여전히 위험 |
| 미리 정한 컬럼 목록에서 **매핑해 고른다** | 안전 |

```java
Map<String, String> allowed = Map.of("date", "created_at", "price", "amount");
String column = allowed.get(sortKey);   // 없으면 기본값
```

사용자 입력이 쿼리에 **직접 닿지 않는다**는 점이 핵심입니다. 입력은 키를 고르는 데만 쓰이고, 실제 컬럼명은 우리가 쓴 문자열입니다.

**판단 기준:** 동적으로 만들어야 하는 것이 문법이면 허용 목록, 값이면 바인딩입니다. 이 구분이 기준입니다.

**흔한 실수:** `LIKE` 검색에서 `%` 를 값에 붙이며 문자열을 조립하는 것. 값 자체는 바인딩해야 하고, 와일드카드는 파라미터 값 안에 넣습니다. 사용자가 넣은 `%` 를 그대로 두면 의도치 않은 전체 스캔이 될 수도 있습니다.

</details>

### 인젝션을 코드 리뷰 없이 잡을 방법이 있나요?

<details>
<summary>답변</summary>

사람 눈에 의존하면 언젠가 새므로 **경로를 막는 장치**를 둡니다.

| 장치 | 무엇을 하나 |
|------|-------------|
| 정적 분석 | 문자열 연결이 쿼리로 흘러가는 경로를 찾아낸다 |
| 쿼리 작성 규약 | 문자열 연결 쿼리 자체를 금지하고 CI 에서 검사 |
| 최소 권한 계정 | 애플리케이션 계정에 DDL, `DROP` 권한을 주지 않는다 |
| 감사 로그 | 비정상적으로 넓은 조회를 사후에 탐지 |

세 번째가 특히 값어치가 있습니다. 인젝션이 성공해도 **피해 범위를 줄입니다.** 조회 전용 기능이 쓰는 계정에 쓰기 권한이 없으면 데이터가 지워지지 않습니다.

**판단 기준:** 방어를 여러 겹으로 둡니다. 바인딩으로 막고, 권한으로 피해를 줄이고, 로그로 탐지합니다. 하나에만 의존하지 않습니다.

**흔한 실수:** WAF 를 두면 된다고 답하는 것. WAF 는 알려진 패턴을 막는 보조 장치입니다. 우회 기법이 계속 나오므로 **애플리케이션 쪽 바인딩을 대체하지 못합니다.**

</details>
