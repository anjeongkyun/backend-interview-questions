# 전달 보장과 멱등 소비자

> 정확히 한 번은 없다. 두 번 와도 괜찮게 만든다

## 이 개념을 왜 묻나

큐를 붙여본 사람과 이름만 아는 사람이 갈립니다. "exactly-once 로 설정합니다"라고 답하면 그 뒤 질문을 못 받습니다. **중복을 없애는 게 아니라 중복이 무해하게 만드는 것**이 실무 답입니다.

## 질문

### at-least-once 와 exactly-once 의 차이는 무엇인가요?

<details>
<summary>답변</summary>

무엇을 포기하느냐의 차이입니다. at-most-once 는 **유실**을, at-least-once 는 **중복**을 감수합니다.

| 보장 | 동작 | 대가 |
|------|------|------|
| at-most-once | 받고 바로 커밋한 뒤 처리 | 처리 중 죽으면 **유실** |
| at-least-once | 처리한 뒤 커밋 | 커밋 전에 죽으면 **중복** |
| exactly-once | 처리와 커밋을 한 트랜잭션으로 | 특정 조건에서만 성립. 범위가 좁다 |

실무 기본은 at-least-once 입니다. 유실보다 중복이 다루기 쉽기 때문입니다.

exactly-once 가 어려운 이유는 **처리 대상이 큐 밖에 있을 때** 커밋과 처리를 한 트랜잭션으로 묶을 수 없다는 것입니다. 외부 결제 API 를 호출하고 오프셋을 커밋하는 두 동작은 원자적으로 묶이지 않습니다.

**판단 기준:** 처리 결과가 같은 저장소 안에 있으면 트랜잭션으로 묶을 수 있어 exactly-once 에 가까워집니다. 외부로 나가면 불가능하다고 보고 멱등하게 만듭니다.

**흔한 실수:** Kafka 의 exactly-once 설정을 켜면 끝난다고 답하는 것. 그 보장은 **Kafka 안에서 읽고 쓰는 경로**에 대한 것입니다. 컨슈머가 외부 API 를 부르거나 다른 DB 에 쓰면 그 구간에는 적용되지 않습니다.

</details>

### 같은 메시지가 두 번 와도 안전하게 만드는 방법은?

<details>
<summary>답변</summary>

**처리한 메시지를 기억하고 두 번째는 건너뜁니다.** 또는 연산 자체를 여러 번 해도 같게 만듭니다.

| 방법 | 예 | 주의 |
|------|-----|------|
| 처리 이력 기록 | 메시지 id 를 유니크 키로 저장 | 이력 저장과 실제 처리가 한 트랜잭션이어야 한다 |
| 조건부 갱신 | `UPDATE ... WHERE status = 'PENDING'` | 상태 전이가 한 방향일 때만 |
| 절대값으로 쓰기 | 재고를 5로 설정 (5 감소가 아니라) | 메시지에 결과값이 담겨야 한다 |

두 번째와 세 번째는 이력 없이도 안전합니다. **연산이 이미 멱등**하기 때문입니다.

```sql
INSERT INTO processed (message_id) VALUES (?);
UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'PENDING';
```

두 문장을 한 트랜잭션에 넣으면, 중복 메시지는 첫 문장에서 유니크 위반으로 걸려 전체가 롤백됩니다.

**판단 기준:** 이력 테이블은 무한히 자랍니다. 메시지 id 에 보관 기간을 두고 지웁니다. 중복은 보통 짧은 시간 안에 오므로 며칠이면 충분합니다.

**흔한 실수:** 처리 전에 "이미 했나" 를 조회해서 막는 것. 조회와 처리 사이에 다른 컨슈머가 끼어들 수 있어 **경합이 그대로 남습니다.** 조회로 막지 말고 유니크 제약이나 조건부 갱신으로 DB 가 막게 해야 합니다.

</details>

### 순서가 중요한 메시지는 어떻게 다루나요?

<details>
<summary>답변</summary>

**순서가 필요한 것끼리 같은 파티션으로 보냅니다.** 전체 순서는 보장할 수 없고, 보장할 필요도 없습니다.

Kafka 는 파티션 안에서만 순서를 지킵니다. 계정 id 를 키로 쓰면 같은 계정의 메시지가 항상 같은 파티션에 갑니다.

| 파티션 | 담긴 메시지 | 보장되는 것 |
|--------|-------------|-------------|
| P0 | A-1, A-2, A-3 | A 계정 안에서의 순서 |
| P1 | B-1, B-2 | B 계정 안에서의 순서 |

P0 와 P1 사이의 순서는 보장되지 않습니다. A 와 B 는 서로 무관하므로 문제가 되지 않습니다.

**판단 기준:** 순서 보장 단위를 좁게 잡을수록 병렬 처리가 늘어납니다. 전체 순서가 필요하면 파티션이 하나여야 하고, 그러면 처리량이 컨슈머 한 대로 묶입니다.

**흔한 실수:** 파티션을 늘리면 순서가 깨진다는 것만 알고 **키 설계로 해결한다**는 답을 못 하는 것. 그리고 재시도를 켜면 같은 파티션 안에서도 순서가 뒤바뀔 수 있습니다. 앞선 메시지가 실패해 재전송되는 동안 뒤 메시지가 먼저 도착합니다. 순서가 중요하면 전송 중 요청 수를 1로 제한하거나 멱등 프로듀서를 켜야 합니다.

</details>
